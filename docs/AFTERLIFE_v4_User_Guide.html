About the figures: screenshots in this guide are deterministic renderings of the real client.py terminal interface using illustrative account/job data. They are not conceptual diagrams, and command names/prompts follow the implementation.

AFTERLIFE is a minimalist freelancer board and forum reachable as a Tor v3 onion service. Version 4 substantially changes the security model and user workflow: the client now talks to Tor directly through SOCKS5h, private chat is end-to-end encrypted in the client, registration and sensitive writes use memory-hard proof-of-work, jobs require worker confirmation before completion, and the platform adds a forum, invite system, trust levels, quotas, and expanded moderation.

Important: the server can read jobs, forum posts, comments, system notices, social-graph metadata, and account relationships while it is running. Only private chat message contents are end-to-end encrypted from the server.

[ 1 ] SECURITY MODEL

DataProtectionWho can read it
Private chat bodiesX25519 + HKDF-SHA256 + ChaCha20-Poly1305, performed by client.pyOnly chat participants holding the private keys
Jobs, forum threads, comments, system noticesFernet encryption at rest with the server master keyRunning server/operator; not readable from a database-only copy

The client validates Tor v3 onion addresses, supports first-contact address pinning in ~/.afterlife/known_hosts.json, strips terminal control characters from server output, and uses a random SOCKS username so Tor can isolate AFTERLIFE circuits from other applications.

[ 3 ] REGISTRATION, LOGIN, AND PROOF-OF-WORK

Figure 2 — Login through the real v4 authentication gateway, including the anti-bot PoW prompt and successful session transition.

3.1 Account rules

FieldRule
Nickname3–12 characters; ASCII letters, digits, underscore. Comparison is case-insensitive and uses a confusable skeleton. Reserved administrative/system-like names are rejected.
Password10–128 characters.
InviteMay be required when registration mode is invite.
ApprovalIf the approval lock is enabled, registration succeeds into a pending state; an administrator must approve before login.

3.2 Login

Login returns a session token. Only one active session per account is kept: a new login replaces existing sessions. Sessions expire after one hour of inactivity.

Failed logins do not hard-lock an account. Instead, the attacking Tor circuit pays increasing PoW difficulty (up to +8 bits), while account-wide difficulty added by failures from other circuits is capped at +3 bits.

3.3 New-account read-only window

For the first 24 hours, normal new accounts are read-only for quota-controlled writes. The server checks this before asking for PoW, so the client does not waste work on an action that would be denied.

[ 5 ] CONTRACT LIFECYCLE

Authors select one accepted worker. Marking a selected job done does not immediately finalize it: the job becomes awaiting_confirmation. The selected worker sees an action-needed notice and can confirm or dispute.

Figure 4 — Selected-worker view when an author requests completion. The worker uses confirm or dispute directly from contract@view.
StatusMeaning
openAccepting applicants.
awaiting_confirmationAuthor requested completion; selected worker must confirm or dispute.
disputedWorker challenged completion; an admin resolves to done/open/cancelled.
doneTerminal completed state. Ratings and completion reputation become eligible.
cancelledNot accepting applications; may be reopened unless already done.
If the selected worker never responds, maintenance automatically finalizes the job after the configured confirmation timeout (default: 7 days).

Withdrawal is final for that contract: once you withdraw, you cannot accept the same job again.

[ 6 ] PRIVATE CONTRACTS

Creating a private job returns a high-entropy private token exactly once. The server stores only a keyed HMAC digest of that token. The token unlocks the description and is required to accept the private job.

Figure 5 — Creating a private contract. The private token is rendered exactly once after a successful create job request.
Store private tokens securely. There is no recovery endpoint. The author/admin can still view the description without the token, but intended workers need the token.

[ 7 ] REPUTATION, TRUST, AND QUOTAS

7.1 Sybil-resistant reputation

Version 4 no longer treats every +1/-1 rating equally. Reputation is weighted by the rater's existing reputation, repeated pairs decay, reciprocal positive ratings are discounted, and positive reputation granted by a rater is budgeted per rolling 24 hours. Fresh accounts therefore cannot create reputation from nothing by rating each other.

Job-completion reputation is also weighted and decayed. Jobs completed less than one hour after creation earn no completion reputation. Negative-rating bursts may be frozen for administrator review rather than applied automatically.

7.2 Rating requirements

A rating now requires a specific completed job_id. A user can rate only a counterparty for that completed job. Ratings are not a generic nickname-only vote.

[ 8 ] END-TO-END PRIVATE CHAT

Chats can be created automatically when a worker accepts a job or manually with chats → open. User message plaintext is limited to 128 characters. The server stores ciphertext together with sender/recipient key fingerprints and refuses messages encrypted to stale keys.

Figure 6 — E2E chat view with the peer fingerprint, system notice, encrypted-message markers, and send command.

Conversation lists and messages are paginated. Message history uses a cursor (before_id) so very large chats do not create oversized responses.

The E2E design uses static X25519 keys and therefore does not provide forward secrecy. A later compromise of a retained private key can expose messages encrypted for that key.

[ 9 ] KEY MANAGEMENT

At registration, the client creates an X25519 keypair. The private key never goes to the server and is stored in ~/.afterlife/keys/<onion>/<nick>.json, encrypted with a key derived from your password using scrypt and ChaCha20-Poly1305.

Figure 7 — Local key-management screen and an export command example. The private key file remains on the user device.
CommandPurpose
keysDisplay current fingerprint and local key information
exportCreate a passphrase-encrypted backup for offline storage or device transfer
importRestore a key backup on another device
rotateCreate and publish a new current public key (max 3 rotations/day)

Peer keys are pinned locally. A changed fingerprint produces a warning and requires acceptance before sending to the new key. Verify fingerprints out of band.

[ 10 ] FORUM

Version 4 adds an authenticated, block-aware forum. Threads use encrypted-at-rest titles/bodies, replies are paginated (20 per page), and thread search uses a keyed HMAC term index so the database does not contain a plaintext keyword index.

Accounts at reputation ≤ -10 cannot create threads or comments. Posting is also governed by trust quotas, rate limits, and PoW.

[ 11 ] INVITES

L2 users and admins can create invitation codes. Default policy: at most 3 new invites per 30 days, at most 5 outstanding, and a 14-day lifetime. Invites can be revoked. If an invitee is banned or wiped, the inviter loses 2.0 reputation once.

The invite menu deliberately warns that vouching links the new account to the inviter. This relationship is server-visible metadata.

[ 12 ] BLOCK LIST

Blocks are bidirectional for interaction. Blocked pairs cannot message, rate, accept each other's jobs, or interact normally through the forum. Lists and detail views filter blocked authors/posts where appropriate. Admin accounts cannot be blocked.

[ 13 ] PROFILE AND PASSWORD

The profile shows nickname, reputation, trust level, distinct job partners, creation time, PoW difficulty/exemption state, administrator flag, and current key fingerprint. profile → password changes the account password. The client re-encrypts the local key file under the new password, and the server invalidates old sessions and returns a replacement session token.

[ 15 ] TROUBLESHOOTING & OPERATIONAL SECURITY

15.1 Onion is unreachable

  1. Verify system UTC time/NTP.
  2. Verify Tor reaches Bootstrapped 100%.
  3. If supported, enable Tor ExtendedErrors for more precise SOCKS failures.
  4. Test the exact onion address through Tor Browser. A server-side “Invalid JSON” response still proves transport reachability.

15.2 Secrets to protect

Never share session tokens, private job tokens, private chat keys, or exported key backups. Verify the server onion address through a signed channel. Do not reuse the AFTERLIFE account password elsewhere.
