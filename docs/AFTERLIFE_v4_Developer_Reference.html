[ 1 ] ARCHITECTURE

The Tor container is the only component with network access. The application container runs with network_mode: none, non-root and read-only hardening, and communicates only through a shared Unix socket. Tor exports per-stream circuit identity using HiddenServiceExportCircuitID haproxy; the application parses the resulting PROXY v1 header and keys connection/rate/PoW controls to circ:<id>.

Blocking SQLite, PBKDF2, and scrypt work runs in a bounded ThreadPoolExecutor (default 16 workers) behind a bounded admission queue (default 256 jobs). New work is shed when the queue is full.

[ 4 ] AUTHENTICATION & SESSIONS

Session tokens are URL-safe random 32-byte tokens. A login invalidates prior sessions for the same user. Idle timeout is 3,600 seconds. Session-wide request limiting defaults to 240 requests/minute. Password changes invalidate sessions and return a fresh token.

Authentication performs a real or dummy PBKDF2 verification before exposing account state, reducing username/state side channels.

[ 5 ] PROOF-OF-WORK PROTOCOL

get_challenge supports purposes: register, login, create_job, create_thread, post_comment, open_chat, accept_job, and rate_user.

Challenge response data:

{
  "required": true,
  "challenge_id": "32 hex chars",
  "prefix": "random hex",
  "difficulty": 5,
  "algorithm": "scrypt-leading-zero-bits",
  "scrypt": {"n":8192,"r":8,"p":1,"dklen":32},
  "expires_in": 600
}

The client searches decimal nonces until scrypt(prefix:nonce, salt=prefix) has at least difficulty leading zero bits. Challenges are removed before verification, so each challenge permits exactly one verification attempt. Session challenges are bound to user ID; login challenges are bound to lowercase nickname; registration is bound to its issuer circuit.

8.1 Pagination

8.2 Job summary/detail

Summary fields: id, title, reward, min_reputation, is_private, status, author_id, author_nickname, author_is_banned, author_display, accept_count, created_at, updated_at, viewer_reputation, not_enough_reputation. My-jobs views additionally expose selected_worker_id and you_are_selected.

8.3 Chat/message

Chat summaries include partner identity, current peer key fingerprint, blocked state, unread count and timestamps. Message objects carry ID, sender identity, type (system or e2e), ciphertext/body, sender/recipient key fingerprints, and creation/read metadata. list_messages returns has_more and next_before_id.

8.4 Forum

Thread summaries: id, title, author_id, author_nickname, author_is_banned, author_display, reply_count, created_at, updated_at. Detail adds decrypted body, viewer flags, and paginated posts.

The master key is an ASCII header plus base64-encoded 32-byte secret written atomically at mode 0600. A database canary causes startup to fail loudly if the wrong key is supplied instead of silently returning empty plaintext.

[ 10 ] REPUTATION, TRUST, AND QUOTAS

Positive rating weight grows with the rater's reputation (full weight at 10). A rater with reputation ≤0 cannot create positive reputation. Pair repetition applies 0.5 decay per prior pair interaction, reciprocal positive ratings are multiplied by 0.5, and each rater has a +3.0/day positive budget. Negative ratings have a minimum weight of 0.1; burst and per-target loss caps can freeze ratings for review.

Job completion has a base grant of 1.0, weighted by employer reputation, daily and pair decay, per-employer caps, and a minimum job age of 3600 seconds.

Trust level derives from account age, reputation, distinct completed-job partners, and admin flag. Rolling quota counters cover create_thread, post_comment, create_job, open_chat, accept_job, send_message.

[ 11 ] REGISTRATION & MODERATION

Registration modes are open, invite, and closed. Adaptive registration PoW begins rising above 20 registrations/hour; a separate hard cap defaults to 200/hour. Approval mode uses a bounded queue of 200 pending accounts with 7-day expiry.

Nicknames are normalized through a confusable skeleton for uniqueness and checked against reserved names. Moderation flags are deduplicated for 6 hours and retained 30 days. They are advisory and include job disputes, rating anomalies, coordinated registration, cross-account duplicate text, fast/unseen-thread replies, and metronomic timing.

Banning or wiping an invitee penalizes the inviter once. Wiping removes the user's jobs/forum content while preserving counterparties' completion history where required.

[ 12 ] ADMIN CONSOLE & MODERATION WORKFLOWS

Administrator functionality is exposed by the same terminal client only when is_admin is true. The main menu then adds admin, which opens the moderation grid implemented by admin_menu(). This is an operator/developer surface and is intentionally documented here rather than in the end-user guide.

The console controls registration mode and approval lock, pending-account decisions, direct reputation adjustment, moderation flags, frozen ratings, contract disputes, bans, and user wipes.

12.3 Destructive/account actions

ban invalidates the target's active sessions and prevents login. wipe is stronger: it bans the account and removes user-owned jobs/forum content according to the server wipe logic while retaining counterparties' records where the data model requires them. The client asks for a yes/no confirmation before either command is sent.

[ 13 ] DEPLOYMENT & CONFIGURATION

setup.sh creates private data/secrets/runtime directories, stores the bootstrap administrator password in a one-time secret file, pins base images by digest, builds hash-locked Python dependencies, verifies the Tor Project repository signing fingerprint, checks Tor PoW module availability, starts the containers, and prints the onion address.

backup_keys.sh creates an AES-256 passphrase-encrypted archive containing the onion key and server master key. Both are irreplaceable.

[ 15 ] TEST COVERAGE & V3 → V4 SECURITY CHANGES

The supplied tests/test_security.py exercises real server instances and includes regressions for slowloris handling, per-circuit connection limits, mandatory PROXY headers, challenge exhaustion, login-difficulty abuse, SimHash overflow, master-key corruption, PoW single-use/binding, sybil reputation farming, bounded pending queues, accept/withdraw abuse, read-only ordering, cheap private-token verification, circuit isolation, moderation-flag deduplication, frozen-rating replay, worker confirmation/disputes, E2E confidentiality/tampering, SOCKS transport, logging/privacy, and related hardening.

Verification performed while preparing these docs: the supplied suite was run in the sandbox and passed tests through the worker-confirmation/dispute regression before the execution window ended; no test failure was observed in that run.

The older documentation is materially outdated in several places: it described protocol version 1, proxychains, 8-character minimum passwords, generic nickname-only ratings, server-side Fernet private messages, thread-pool TCP handling, a three-state job lifecycle, and no forum/invite/trust/PoW system. Those descriptions have been replaced here with the v4 implementation.
